```java
public final class ArbolNario<T> {                    // en estructuras/, sin dependencias del dominio
    private final T valor;
    private final ArrayList<ArbolNario<T>> hijos;

    public ArbolNario(T valor)                          // O(1)
    public T valor()                                    // O(1)
    public ArbolNario<T> agregarHijo(T valor)           // O(1) amortizado; devuelve el subárbol nuevo
    public boolean eliminarHijo(ArbolNario<T> hijo)     // O(k), k = número de hijos (busca y desplaza)
    public List<ArbolNario<T>> hijos()                  // O(1), vista no modificable
    public boolean esHoja()                             // O(1)
    public List<T> preorden()                           // O(n): nodo, luego hijos de izquierda a derecha
    public List<T> postorden()                          // O(n): hijos, luego el nodo
    public <R> R reducirPostorden(BiFunction<T, List<R>, R> combinar)   // O(n)
}
```

- **Clase recursiva** ("un árbol es un valor más una lista de árboles"), sin una clase `Nodo` aparte.
- **`reducirPostorden`** sirve para los totales por rama del dashboard: cada nodo combina los resultados ya
  calculados de sus hijos. **Pregunta abierta:** ¿se incluye, o el commit 9 se limita a los dos recorridos del plan?
- **Recursión y no una pila explícita:** la profundidad es 3, así que no hay riesgo de desbordar la pila de llamadas.
  La versión iterativa con `ArrayDeque` se menciona como alternativa en el documento explicativo.
- **El valor es final.** Cambiar el valor de un nodo, que hará falta para el reemplazo de una máquina, se propone en
  el commit 17.
- **Pruebas:**
  - un árbol de un solo nodo;
  - preorden `A B D E C` y postorden `D E B C A` sobre el árbol `A → (B → D, E), C`;
  - `reducirPostorden` suma los valores por rama;
  - `eliminarHijo` quita el subárbol completo, y devuelve `false` si el nodo no es hijo directo.

## 3. Decisiones tomadas en esta sesión (para defender en clase)

### 3.1 Las acciones del servicio devuelven su DTO (commit 6)
Al principio el controlador llamaba a `servicio.paso()` y después a `servicio.estadoSimulacion()`. Eso usa **dos
candados distintos**, y el reloj podía avanzar un tick entre las dos llamadas. Ahora cada acción devuelve su DTO
armado dentro del mismo método `synchronized`, así la respuesta refleja exactamente el efecto de la acción. Es la
misma idea de la regla 4 de la sección 4: la foto se construye dentro del candado.

### 3.2 La cola circular viaja en orden físico, con `null` en las celdas vacías (commit 5)
El frontend tiene que dibujar el arreglo fijo con los punteros `frente` y `final`, no una lista en orden de
llegada. Por eso no se usa `List.copyOf`, que rechaza los `null`: se copia a una lista nueva y se envuelve como no
modificable.

### 3.3 Los rechazos siguen quedando en la bitácora (commit 7)
En la Entrega 1 el modelo anotaba en la bitácora los rechazos de inyectar un fallo y de deshacer con la pila vacía.
Para no perder esas líneas, el servicio mira primero si la acción se va a rechazar, deja que el modelo haga su
registro y después lanza la excepción que se convierte en `409`. Deshacer un comando que la simulación ya invalidó
responde `200`, porque es un caso normal del diseño (sección 8), no un error.

### 3.4 Dependencia entre `servicio` y `api.dto` (commit 5)
El servicio importa los DTOs, porque la regla 4 exige construirlos dentro del método sincronizado, y la API importa
el servicio. Es una dependencia de ida y vuelta entre esos dos paquetes. **El modelo no se ve afectado**: sigue sin
conocer a nadie. La alternativa sería mover `dto/` a `servicio/`, pero contradice el árbol de la sección 4.

### 3.5 Otras decisiones menores
- Las excepciones `NoEncontradoException` (404) y `AccionNoPermitidaException` (409) viven en `servicio/`. El
  servicio decide y lanza la excepción; los controladores no tienen `try`/`catch`.
- Hay dos controladores: `ControladorSimulacion` controla la simulación y `ControladorOperador` recibe las acciones
  del operador. Una responsabilidad por clase.
- CORS permite cualquier puerto de `localhost` y `127.0.0.1`. Los orígenes están en `application.properties`.

## 4. Hallazgos técnicos
- En Spring Boot 4, `@AutoConfigureMockMvc` está en `org.springframework.boot.webmvc.test.autoconfigure`.
- Las pruebas MockMvc comparten el contexto de Spring, y con él el servicio. Por eso cada prueba empieza con
  `servicio.reiniciar()`, que además deja la simulación en pausa para que el reloj no interfiera.
- El modelo es determinista en el tick 0 (todas las máquinas operando y sin fallos), así que las pruebas de las
  acciones no dependen del azar.
- Un `java -jar target/simulador-planta.jar` sin `--server.port` ocupa el puerto 8080 y no termina solo: para
  pruebas manuales, levantarlo en otro puerto y detenerlo al terminar.
